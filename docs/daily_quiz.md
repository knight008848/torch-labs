## 📌 W1（Day 1-7）｜地基 I：Tensor 与 autograd

### Day 02｜Tensor 三要素与 NumPy 内存桥

- **Q1（温故 Day 1）**：在环境检查中，为什么在 WSL 的 `pydata` 或 `base` conda 环境下执行 `import torch` 会失败，必须使用 `embodied_ai`？
  - **A**：`pydata` 是精简环境未安装 PyTorch，适配 CUDA 12.x 的 PyTorch 仅安装在 `embodied_ai` 中
  - **B**：`pydata` 环境需要插显示器才能加载 PyTorch 的动态链接库
  - **正确答案**：`A`
  - **要点解析**：环境隔离与依赖真实现状校验（防止混淆环境导致模块缺失，归类 K）。
- **Q2（知新 Day 2）**：当使用 `torch.from_numpy(arr)` 将 CPU 上的 NumPy 数组转换为 PyTorch Tensor 时，底层内存行为是怎样的？
  - **A**：进行深拷贝（Deep Copy），修改 `arr` 原数组不会改变 Tensor
  - **B**：零拷贝共享底层内存缓冲区（Zero-copy Shared Memory），就地修改 `arr` 会直接导致 Tensor 内容变化
  - **正确答案**：`B`
  - **核心陷阱**：`torch.from_numpy` 共享内存；若需独立必须显式 `.clone()`（归类 C/A）。

### Day 03｜形状手术：view / reshape / permute

- **Q1（温故 Day 2）**：在具身感知中，为什么磁盘存储的原始观测图像通常用 `uint8`，而送入网络前要转为 `float32`？
  - **A**：`uint8` 比 `float32` 节省 75% 内存与 I/O 带宽；反向传播梯度求导需要连续的浮点动态范围
  - **B**：PyTorch 的卷积算子硬件上只能接收浮点数，不能接收整数
  - **正确答案**：`A`
  - **要点解析**：数据存储字节与数值计算精度的分工（归类 T02）。
- **Q2（知新 Day 3）**：对一个 `[84, 84, 3]` 的图像张量执行 `t.permute(2, 0, 1)` 后，为什么立即调用 `t.view(3, 84*84)` 会报错？
  - **A**：`view()` 只能用于 2 维张量，不能用于 3 维张量
  - **B**：`permute()` 仅改变步长（strides）而未搬移物理内存，导致张量在内存中不再连续（`.is_contiguous() == False`）
  - **正确答案**：`B`
  - **核心陷阱**：`view()` 强依赖内存连续性，非连续张量必须先 `.contiguous()` 或使用 `reshape()`（归类 T04）。

### Day 04｜索引、切片与布尔掩膜

- **Q1（温故 Day 3）**：如果希望改变张量形状且不关心其物理内存是否连续，应该优先调用哪个 API？
  - **A**：`tensor.view(...)`
  - **B**：`tensor.reshape(...)`
  - **正确答案**：`B`
  - **要点解析**：`reshape()` 在连续时返回视图，在非连续时自动拷贝保底（归类 T04）。
- **Q2（知新 Day 4）**：在截取机器人动作序列时，表达式 `actions[0:1, :]` 与 `actions[0, :]` 返回张量的维度有何区别？
  - **A**：两者完全一致，都是 1 维张量 `[7]`
  - **B**：切片语法 `0:1` 保留了批次/时间维度返回 `[1, 7]`，而整数索引 `0` 会降维返回 `[7]`
  - **正确答案**：`B`
  - **核心陷阱**：保持维度（keepdims）对下游批处理拼接和广播至关重要（归类 T05）。

### Day 05｜广播与 in-place 陷阱

- **Q1（温故 Day 4）**：若有一个 `[N, 7]` 的轨迹张量，如何不使用 for 循环筛选出第 0 维关节角大于 0.5 的所有帧？
  - **A**：使用布尔掩膜 `mask = trajectory[:, 0] > 0.5`，然后 `trajectory[mask]`
  - **B**：使用 `torch.split` 逐帧判断
  - **正确答案**：`A`
  - **要点解析**：布尔索引向量化高效筛选（归类 T05）。
- **Q2（知新 Day 5）**：在构建需要反向传播的计算图时，为什么应当极力避免 `x += 1` 或 `x.add_(1)` 这类就地（in-place）操作？
  - **A**：就地操作会覆写反向传播所依赖的中间前向激活值，导致 autograd 报错
  - **B**：就地操作会导致 GPU 显存泄漏
  - **正确答案**：`A`
  - **核心陷阱**：autograd 依赖计算图节点保存的历史张量版本，修改已有内存会破坏微分链（归类 T07）。

### Day 06｜autograd 动态计算图

- **Q1（温故 Day 5）**：形状为 `[16, 7]` 的动作张量与形状为 `[7]` 的均值张量相减，能否触发广播？结果形状是什么？
  - **A**：不能，维度数不一致
  - **B**：能，尾部对齐，均值自动向左扩展匹配，结果为 `[16, 7]`
  - **正确答案**：`B`
  - **要点解析**：PyTorch 尾部对齐广播规则（归类 T06）。
- **Q2（知新 Day 6）**：每次迭代计算完梯度后，为什么必须显式调用 `optimizer.zero_grad()`？
  - **A**：PyTorch 默认累加梯度（`grad += new_grad`），如果不清零会导致梯度值被多次累积而爆炸
  - **B**：不清零会导致显存立即耗尽崩溃
  - **正确答案**：`A`
  - **核心陷阱**：梯度累积语义的存在理由与默认行为（归类 G04）。

### Day 15｜HDF5 结构探针与懒加载机制

- **Q1（温故 Day 13）**：如何将像素值在 `[0, 255]` 的 uint8 张量转换为模型可接受的标准化输入？
  - **A**：转为 float32 并除以 255.0，缩放到 `[0.0, 1.0]`
  - **B**：使用整数除法直接减去 128
  - **正确答案**：`A`
  - **要点解析**：像素动态范围标准化（归类 P03）。
- **Q2（知新 Day 15）**：在 h5py 中，`dataset[0]` 与 `dataset[:]` 在内存使用上有什么本质区别？
  - **A**：完全相同，都会将几十 GB 数据全部载入内存
  - **B**：`dataset[0]` 是单帧懒加载切片，只读取该帧几十 KB 数据；`dataset[:]` 会一次性将全量数据读入 RAM 导致内存暴增
  - **正确答案**：`B`
  - **核心陷阱**：懒加载切片防内存溢出（归类 P04）。

### Day 17｜fork 死锁原理与复现

- **Q1（温故 Day 16）**：在映射整个数据集的全局帧索引时，如何定位某个全局索引属于哪一条 demo 轨迹及轨迹内的偏移？
  - **A**：通过预先统计各 demo 的累计帧数（Cumulative lengths），使用二分查找或区间划分定位
  - **B**：每次都从头遍历所有 demo
  - **正确答案**：`A`
  - **要点解析**：全局线性索引映射算法（归类 P04）。
- **Q2（知新 Day 17）**：为什么 HDF5 预打开句柄的 fork 死锁在 `num_workers=0` 时不会触发，而在 `num_workers=2` 时会崩？
  - **A**：`num_workers=0` 运行在主进程单线程中，不发生跨进程复制（fork），因而不会遭遇进程间互斥锁状态混乱
  - **B**：`num_workers=0` 会自动把文件复制一份到临时目录
  - **正确答案**：`A`
  - **核心陷阱**：隔离故障域，确认该问题仅发生在多进程 IPC 场景（归类 P05）。

### Day 18｜worker_init_fn 修复

- **Q1（温故 Day 17）**：Linux 环境下进程 fork 时，底层 C 库（如 HDF5 / libhdf5）的状态会如何？
  - **A**：内部互斥锁（Mutex）与打开的文件描述符被浅层拷贝到子进程中，但子进程并不知道这些锁已在上锁状态，导致死锁
  - **B**：子进程会自动重新初始化所有 C 库
  - **正确答案**：`A`
  - **要点解析**：fork 语义与非 fork-safe C 库的本质冲突（归类 P05）。
- **Q2（知新 Day 18）**：在 DataLoader 中配置 `worker_init_fn` 的目的是什么？
  - **A**：为每一个独立的 worker 进程提供初始化钩子，让每个子进程各自独立打开私有的文件句柄或设置独立的随机种子
  - **B**：把主进程的显存空间分配给子进程
  - **正确答案**：`A`
  - **核心陷阱**：多进程资源隔离标准解法（归类 D05, P06）。

### Day 26｜I/O 甜点扫描

- **Q1（温故 Day 25）**：单独设置 `pin_memory=True` 但在向 GPU 转移时调用 `tensor.to('cuda', non_blocking=False)` 能否实现计算与传输重叠？
  - **A**：不能，`non_blocking=False` 是同步阻塞调用，CPU 会一直等待数据拷贝完成
  - **B**：能，PyTorch 会自动把它变成异步
  - **正确答案**：`A`
  - **要点解析**：`pin_memory` 必须配合 `non_blocking=True` 才能真正异步重叠（归类 B05）。
- **Q2（知新 Day 26）**：在 DataLoader 超参调优时，为什么不能把 `num_workers` 和 `prefetch_factor` 设得无限大？
  - **A**：过多的工作进程会造成 CPU 线程频繁上下文切换争抢开销，且队列过深会导致主机内存被未消费的 Batch 挤爆
  - **B**：PyTorch 强制限制 `num_workers` 最大只能为 2
  - **正确答案**：`A`
  - **核心陷阱**：I/O 队列长度与硬件资源的平衡甜点（归类 P10, D04）。
